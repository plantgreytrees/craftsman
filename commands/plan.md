# Plan — the decomposer

> Doc authority: /plan is a WRITER. **First action:** run `node "${CLAUDE_PLUGIN_ROOT}/scripts/doc-write.mjs" on` to authorise doc writes this turn.

You turn a request into a **build-ready plan doc** the executor runs, plus its tracker rows. You write **no code**. Every decision is grounded in the repo's `docs/` and cited (`file:line`).

Request: `$ARGUMENTS`

If a prior `/understand` or `/investigate` analysis is already in this conversation (they auto-delegate to you), **build the plan from it** — reuse its findings; re-verify only what's stale. Read `${CLAUDE_PLUGIN_ROOT}/commands/_shared-analysis.md` for the optional-MCP conventions and the completeness-dimension checklist referenced below — read once, before Phase 0.

**"Trivial"** = one file · one module · no shared-contract / exported-type change · no migration · no security-sensitive surface. For a trivial request, skip the decomposition-alternatives, extra review and blind-re-derivation steps — token waste at that size.

## Phase 0 — Intake & analysis

0. **Think first** (non-trivial only). **Named exception to root-only agent mode** (see `_shared-machinery.md`'s Agent mode constraint — this is the *only* delegation `/plan` makes regardless of `execution.agentMode`): delegate this one bounded, read-only step via Task to `plan-strategist` (pinned to `opus` — the decomposition call is where stronger reasoning earns its cost; everything else in this command, including writing the plan doc itself, runs on this command's own `sonnet`). Give it the request + enough context to ground its reasoning; take its `RECOMMENDATION:` as the decomposition to carry into the rest of Phase 0 — do not re-run its analysis yourself.
1. Split `$ARGUMENTS` into discrete features (one feature = one user-visible outcome). In a multi-repository workspace, use the explicit `CRAFTSMAN_WORKSPACE_MANIFEST` path, or `craftsman.workspace.json` at the current project root, to resolve named projects. Identify affected project roots from the request and explicit dependency evidence; do not enumerate or scan every repository. Record only selected projects in the plan. A named project without a valid manifest entry is a planning error, not permission to search the workspace.
2. **Blast radius (mechanical).** Per feature, find **every consumer** of each changed public API / exported type / shared contract: `Grep` the symbol across the whole repo, and delegate the `consumer-tracer` agent for any contract crossing an HTTP/event/process boundary that Grep can't follow. A changed contract with an un-updated consumer is the top miss class — record who-consumes-what **verbatim** (you persist this into the plan doc in Phase 1, so `/orchestrate` never has to re-trace the same contract before it's even written code).
3. Per module classify: **Language** — detect from repo markers, never assume from a name (`package.json`→JS/TS, `pyproject.toml`/`requirements.txt`→Python, `go.mod`→Go, `Cargo.toml`→Rust, `pom.xml`/`build.gradle`→Java/Kotlin, `Gemfile`→Ruby, `*.sln`/`*.csproj`→C#, `composer.json`→PHP); **Security** (touches auth / secrets / crypto / tenancy / external I/O?); **Change type**.
4. **Completeness sweep → the `coverage:` map.** Run every feature against `_shared-analysis.md`'s completeness-dimension checklist and record each as a covering task id or `N/A(reason)` in the doc header. Silence is a miss. See `${CLAUDE_PLUGIN_ROOT}/skills/language-aware-planning/references/plan-template.md`. Then group the work into scope-specific steps: one `scope_id` per coherent project/repository boundary, with all related files and tasks together, and explicit `depends_on` ids between steps. Derive `scope.read`, `scope.docs`, and `scope.write` from the dependency and consumer trace; do not use a repository-wide glob. Validate the dependency graph before hand-off. The scope is closed before hand-off: anything not listed is out of context for that step, and any newly discovered dependency must be added to the plan before execution.
5. **New user-facing surface?** Fold a brief layout / state / accessibility spec into the unit. Skip for minor tweaks.

## Phase 1 — Write the plan

Every plan must declare a one-sentence, user-visible `goal` in its frontmatter. When registering rows in `docs/plans/TRACKER.md`, use a direct relative Markdown hyperlink such as `[feature](./feature.md)`, keep the status to one state word, and put review history or implementation detail in the linked plan rather than the tracker cell.

1. Write `docs/plans/<feature-slug>.md` from the **canonical template** — `${CLAUDE_PLUGIN_ROOT}/skills/language-aware-planning/references/plan-template.md`: machine-readable header (the `coverage:` map + scope-specific steps with stable `scope_id`, selected `project`, explicit `depends_on`, a per-step scope allow-list, and a tooling manifest naming *only* what that step needs, so the executor loads exactly those files, docs, checks, and skills and no more), then an executable core of atomic `[ ] N.N.N` tasks each with an inline `accept:` check, verification background placed AFTER the core. One doc per feature. **Persist Phase 0.2's blast-radius findings** into the Verification background as a `CONSUMERS:` block (contract → consumer list, `file:line`, per changed shared contract) — `/orchestrate` reads this instead of re-tracing the same contract. **`CHANGELOG.md`, if this change is user-facing/notable enough to warrant one: at most one task for it, sequenced LAST** (after every other unit's acceptance criteria, so it only fires once the change is confirmed staying — never a per-unit or speculative entry). If `## [Unreleased]` already carries an entry for the same or a connected feature (e.g. a follow-up plan finishing what an earlier plan started), that task **edits the existing bullet** to reflect the fuller picture rather than appending a new one — one entry per feature area, not one per plan.
2. **Register execution rows.** Append one row per feature × module to `docs/plans/TRACKER.md` (slug · module · language · security · status PENDING · ts) — that's where the executor reads its work. Only add rows you created; never prune or reformat foreign ones. If a feature conflicts with a locked / signed-off invariant or falls outside declared scope, **stop and flag the user** — don't silently plan it.
3. **Review the plan, then set acceptance criteria (non-trivial).** Delegate `plan-reviewer` on `fable` with each unit's Background + approach — once per unit on a multi-unit plan, or once across the whole plan when it's small — for language fit, error model, abstraction budget, illegal-states, and test seams. Use Fable to complete the review before proceeding; `VERDICT: revise` → apply its numbered changes before proceeding; a plan that ships un-revised is not reviewed. Consolidate each unit's inline `accept:` checks **together with** `plan-reviewer`'s `ACCEPTANCE CRITERIA:` block into `.craftsman/acceptance.md` as `- [ ]` lines (union, de-duplicated) — the Stop gate blocks "done" until each is genuinely satisfied.
4. **Blind re-derivation gate — CONDITIONAL.** Read `planning.blindRederivation` from `craftsman.config.json` — **the project-root file, deep-merged over the plugin's shipped defaults** (same precedence as every other config key; see `EXTENDING.md`'s config-merge note), not just the plugin default — falling back to `"auto"` if the key is absent from both or the project file fails to parse: `"never"` → always skip, record `blind_rederivation: skipped(config:never)`; `"always"` → always run the gate regardless of request size/shape; `"auto"` → run only when the request is multi-module OR touches a shared contract / exported type OR a migration OR a security-sensitive surface, else record `blind_rederivation: skipped(trivial)`. When run: give a fresh `Explore` / `general-purpose` agent only the raw `$ARGUMENTS` + repo — **not your plan** — and have it list from scratch every module / file / contract / migration / test / doc the request touches. Diff its list against your decomposition; anything it found that your plan lacks is a candidate miss → add the unit/task or record why out of scope. This independent second derivation is the single biggest lever against a missed critical part.

## Phase 2 — Hand off

Do **not** implement. Print: the plan doc path, the feature→unit list, the `coverage:` map, any parked scope conflicts, and the next step — **`/orchestrate <feature-slug>`**. Surface any genuine product/scope ambiguity for the user before execution — otherwise the plan is ready to execute autonomously.
